# 2REK1G03VI1902 packet notes

An LG kimchi refrigerator (`Global_Pvictoria_WiFi ThinQ2.0`, deviceType 102), read on
2026-08-19. The appliance speaks the AABB protocol and is monitor-only: its model schema
sets `Config.supportControl` to `false` and the account lists it with
`controllableYn: "N"`, so nothing here is writable.

## Status record

Both `11 EB` (11 bytes) and `11 EC` (20 bytes, status at offset 11) carry the same
nine-byte record.

| Byte | Meaning              | Notes                                                                  |
| ---: | -------------------- | ---------------------------------------------------------------------- |
|    0 | `monStatus`          | 0 fail, 1 not working, 2 normal                                        |
|    1 | `room1Temp` — top    | Storage mode, not a temperature                                        |
|    2 | `room2Temp`          | The right-hand top compartment of the wider models; always `0xFF` here |
|    3 | `room3Temp` — middle | Storage mode                                                           |
|    4 | `room4Temp` — bottom | Storage mode                                                           |
|    5 | `freshAirFilter`     | Always `0xFF`; the appliance has no such feature                       |
|    6 | `oneTouchFilter`     | 0 off, 1 running                                                       |
|    7 | `displayLock`        | 0 released, 1 locked                                                   |
|    8 | `atLeastOneDoorOpen` | 0 closed, 1 open — any compartment                                     |

`0xFF` is the appliance's ignore value and is never published.

## Compartment modes

The bytes that look like a temperature are storage mode codes. The schema maps them
through `roomNTemp_C`, and each compartment has its own list — the same number means a
different thing in each one. `Config.roomConfig` names only room1, room3 and room4 for
this model, which is why room2 is absent.

Home Assistant shows both readings for each compartment: the decoded mode and, under
the entity id it has always had, the raw byte. The raw sensor is still declared as a
temperature in degrees Celsius, which the value is not, but it carries the existing
Home Assistant history for these compartments and so it stays.

The Korean wording is LG's own. It comes from the Korean product-type language pack,
which the account returns when `x-language-code` is set to `ko-KR` — the account's own
language is English, so the default pack gives English strings instead.

Confirmed live: the appliance reported `02 00 FF 03 00 FF 00 01 00`, which reads as
normal monitoring, 맛지킴 김치 중 on top, 야채/과일 중 in the middle and 맛지킴 김치 중
at the bottom. Home Assistant shows exactly those three values.

## Model schema shortcuts worth reusing

- `MonitoringValue.<key>.targetKey` points at the enum that decodes a value which is
  declared as a plain range, which is how the mode tables were found.
- `Config.roomConfig` says which compartments the model actually has.
- For TLV appliances the same file carries the local tag id in each value's `label`,
  for example `opmode_state_tlv_505` for `0x1F9`.

## Compartment power and deodorizing

Both features the appliance's front panel calls 전원 꺼짐 and 탈취 are already visible
without any new field:

- **Compartment power off** is a storage mode, not a separate flag. Each compartment's
  mode list ends with its own off value — 상칸 꺼짐 (9), 중칸 꺼짐 (13) and 하칸 꺼짐
  (9) — which is what the appliance's own guide text means by "일부 칸의 전원이
  꺼졌습니다".
- **Deodorizing** is `oneTouchFilter`, byte 6. LG's Korean name for it is 원터치 탈취,
  and its push messages read "원터치 탈취 기능이 설정되었습니다". The entity uses that
  name.

`freshAirFilter` (청정탈취, off/auto/power) is the second deodorizing feature in the
schema, but this model does not have it: byte 5 reads the ignore value and the appliance
has no such control.

## Neither is controllable

There is nothing to write. `Config.supportControl` is `false`, `ControlWifi.basicCtrl`
carries an empty `data` object, and the account lists the appliance with
`controllableYn: "N"` — the ThinQ app cannot change anything on this refrigerator
either, so the schema documents no control command to implement from.

Sibling refrigerator handlers send an `F0 17` frame that echoes the whole status record
with a single byte replaced. Applying that shape here would be a guess about both the
frame and the byte, on an appliance whose contents depend on the setting, so it is not
attempted. A capture of the appliance being operated from its own panel is the
prerequisite for revisiting this.

## Confirmed by operating the appliance

Captured on 2026-08-19 while the appliance was worked through by hand, one change at a
time. This settled the byte layout and checked the mode tables against real values rather
than the schema alone.

- **Byte 6 and byte 8 were the wrong way round.** Pressing 원터치 탈취 moved byte 6;
  opening a door moved byte 8. The handler had read them in the opposite order, so the
  door sensor showed the deodorizing cycle and the other way about. The schema's key
  order — `oneTouchFilter`, `displayLock`, `atLeastOneDoorOpen` — was right after all.
- **The door flag is shared.** Opening the top compartment and then the middle one moved
  the same byte, so it is the appliance's "at least one door open" flag.
- **Byte 7 is the panel lock**, 1 while locked, confirmed by releasing and re-engaging it.
- **The mode tables are right.** Stepping the mode button through each compartment
  produced 0–7 on the top, 0–7 and 11 in the middle, and 0–8 at the bottom. The values
  the middle compartment skips — 8, 9 and 10 — are the three 유산균 김치+ levels, which
  the appliance sets from within mode 7 rather than from the mode button.
- **The off codes are right**: turning the top compartment off reported 9, and the middle
  and bottom reported 13 and 9 when they went off in turn.
- **Byte 5 is not used on this model.** The owner confirms the appliance has no 청정탈취
  feature, which matches the byte reading `0xFF` in every capture.
