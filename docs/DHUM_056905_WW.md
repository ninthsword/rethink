# DHUM_056905_WW packet notes

Captured on 2026-08-18 from an LG DQ203PECA dehumidifier while it remained registered in the user's ThinQ home.

## Verified cloud controls

ThinQ v2 accepts a single-property control request at the device control endpoint.

- Power uses `ctrlKey=basicCtrl`, `command=Operation`, `dataKey=airState.operation`.
- Target humidity uses `ctrlKey=basicCtrl`, `command=Set`, `dataKey=airState.humidity.desired`.
- `dataSetList` and `dataGetList` are `null` for both forms.

Verified local packets:

| Action              | Packet                             |
| ------------------- | ---------------------------------- |
| Power on            | `01010400000065020100027DC163E3`   |
| Power off           | `01010400000065020100027DC073C2`   |
| Target humidity 50% | `010104000000650201000394D032D182` |
| Target humidity 55% | `010104000000650201000394D0378127` |

The appliance was restored to power off, smart mode 17, fan value 6, and target humidity 55% after testing.

## Verified state fields

| ThinQ field         |     TLV | Conversion                              |
| ------------------- | ------: | --------------------------------------- |
| Operation           | `0x1F7` | 0 off, 1 on                             |
| Operation mode      | `0x1F9` | supported capability bits 17 through 21 |
| Fan strength        | `0x1FA` | enum; this unit accepts only 2 and 6    |
| Target humidity     | `0x253` | 30% through 70%, step 5%                |
| Current temperature | `0x1FD` | raw value divided by 2                  |
| Current humidity    | `0x336` | percent                                 |
| Diagnostic code     | `0x221` | 0 normal                                |

## `0xA8` push snapshot

This model also emits an 86-byte, CRC16-protected frame with kind `0xA8` after a
local or cloud-side state change. Unlike the ordinary `0xA7` response, its 76-byte
payload is a fixed record rather than TLV. Captures used variants `0x66` and `0x67`
and the model signature `01 49 0A 01 0D` at payload bytes 1 through 5.

The following offsets were confirmed by pairing `0xA8` snapshots with ordinary
`0xA7` values and by setting reservations of 60, 120, 240, 300 and 420 minutes:

| Payload offset | Width | Meaning                    | Published as |
| -------------: | ----: | -------------------------- | ------------ |
|              8 |     1 | Power                      | `0x1F7`      |
|              9 |     1 | Operation mode             | `0x1F9`      |
|             10 |     1 | Target humidity            | `0x253`      |
|             11 |     1 | Fan strength               | `0x1FA`      |
|          12–13 |     2 | Configured timer, BE       | not published |
|          14–15 |     2 | Remaining timer, BE        | `0x21B`      |
|             47 |     1 | Temperature, half-degrees  | `0x1FD`      |
|             48 |     1 | Current humidity           | `0x336`      |

All other bytes remain raw and unhandled. `0xA8` is only a common envelope: a
`WINF_056905_WW` capture has a different signature and a much longer record, so its
offsets must not be inferred from this dehumidifier layout.

## Verified mode and fan controls

Captured on 2026-08-19 with the appliance powered on. Every packet below was also
produced byte-for-byte by the LG cloud itself when the same change was requested through
`airState.opMode` / `airState.windStrength`, which is how the encoding was confirmed.

| Action                | Packet                             |
| --------------------- | ---------------------------------- |
| Operation mode = fast | `01010400000065020100037E50128988` |
| Fan speed = low       | `01010400000065020100027E824E17`   |
| Fan speed = high      | `01010400000065020100027E860E93`   |

The capability response carries the supported values as bitmaps, one bit per raw value:

| Capability |     TLV | This unit                        |
| ---------- | ------: | -------------------------------- |
| Modes      | `0x2C1` | `0x3E0000` — 17, 18, 19, 20, 21  |
| Fan speeds | `0x2C2` | `0x11044` — 2 (low) and 6 (high) |

Both match `support.airState.opMode` and `support.airState.windStrength` in the model
schema, where the schema numbers the same values one higher. Fan values 0, 4, 7 and 8
were each acknowledged by the appliance and then dropped with no state report, so only
the two bits it advertises are offered.

Observed appliance behaviour worth knowing:

- Selecting silent mode forces the fan to 2 and the appliance reports both changes.
- Changing the fan while in fast mode drops the appliance back to smart mode, which it
  also reports. Fast mode implies its own fan speed.
- `0x2D7`/`0x2D8`/`0x2D9` repeat as a triplet per mode and look like a per-mode fan
  range, but `0x2D9` tracks whatever fan value is currently selected rather than a
  limit. It is not usable as a capability.

The appliance was restored to power off, smart mode, fan high and target humidity 55%
after testing.

## UVnano, water tank light and the turn-off reservation

Captured on 2026-08-19. Each write was injected on the running appliance and the
appliance reported the new value back, which is what confirms it.

| Action                    | Packet                                                              | Appliance reported    |
| ------------------------- | ------------------------------------------------------------------- | --------------------- |
| UVnano off / on           | `0101040000006502010002A880D1D4` / `0101040000006502010002A881C1F5` | `0x2A2`               |
| Water tank light off / on | `01010400000065020100028780C70C` / `01010400000065020100028781D72D` | `0x21E`               |
| Turn-off reservation 1 h  | `010104000000650201000386D03C1D4F`                                  | `0x21B` counting down |
| Turn-off reservation off  | `010104000000650201000286C0BCF9`                                    | `0x21B`               |

The reservation packet is also exactly what the LG cloud sends for
`airState.reservation.targetTimeToStop = 60` through its `reservationCtrl` command, so
that one is confirmed from both directions. `SupportReserve` advertises
`@AP_SIMPLE_TIMER_DHUM_8`, hence the eight hour limit, and the value is in minutes: one
minute after setting an hour the appliance reported 59.

Automatic drying is **not reported over Wi-Fi**, and not writable either.

The first attempts were inconclusive because the manual says the feature only engages
after the appliance has run for at least four minutes with it set, and they were all
shorter. The test was repeated properly on 2026-08-19: auto dry set from the appliance's
own button, thirty minutes of running, then stopped and left alone for over twenty
minutes, which is when auto dry does its work.

Neither `0x20E` nor `0x225`, the tags the model schema names for auto dry and its
remaining time, appeared at any point. Writing `0x20E` is separately acknowledged and
dropped with no state report, and the capability word `0x2CC` — the bit the RAC and PAC
handlers use to gate auto dry — reads zero. The appliance has the feature on its panel;
it simply does not put it on the wire.

The only tags that moved when the appliance stopped were `0x232` and `0x233`, which read
25 and 12 while running and fell to zero three quarters of a minute after it was switched
off. They track something about the running cycle and are not auto dry, which starts
rather than stops at that moment.

## Deferred controls

- Child lock, swing, start reservation, and filter/energy data are present in the model
  schema but are not writable in Rethink until each command and rollback is captured.
- Air removal (`0x360`) was tried and withdrawn. The appliance acknowledges the write and
  leaves the value at 0, so the switch could only report back what it had been told.

## Water tank full

Captured on 2026-08-19 by filling the tank until the appliance raised the warning and then
emptying it. The appliance does **not** use `0x186`, the tag the model schema names for a
full tank. It sends a notification as a pair instead:

| Event   | Packet contents            |
| ------- | -------------------------- |
| Raised  | `0x2B1 = 256`, `0x2B2 = 1` |
| Cleared | `0x2B1 = 256`, `0x2B2 = 0` |

`0x2B1` identifies which notification and `0x2B2` whether it is raised, so the state is
only meaningful once the id says this is the water tank. Both tags arrive in the same
packet with the id first. The appliance kept running with a full tank rather than
stopping, and removing the tank altogether changed nothing at all — only a genuinely full
tank raises it.

The Home Assistant implementation exposes power, target humidity, operation mode and fan
speed as writable — exactly the four keys the model schema lists under its `basicCtrl`
control command. Temperature, current humidity and the diagnostic code are read-only.

Mode and fan writes are suppressed while the appliance is powered off, where it
acknowledges them and then ignores them.
